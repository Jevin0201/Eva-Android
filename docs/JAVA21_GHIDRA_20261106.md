# Java 21 与 Ghidra 手机端修复

2026-11-06，已保留数据覆盖安装 `0.0.63-java21`。本轮使用已有 Alpine 3.22 aarch64 环境，增加进程级 Java 21 映射兼容层，并安装与手机 REA 6.8.0 对应的 Ghidra 12.1.4。

## 原因与实现

原版 OpenJDK 21.0.11 在 `check_pax()` 对单页执行 `mprotect(RWX)` 时返回 EACCES。诊断捕获到探测页与当前线程栈处于同一个匿名 VMA。独立分配的 RWX 内存成功，给探测页增加保护边界或先隔离该页后，原有权限请求成功。

Linux 6.6 的 SELinux 钩子按当前 VMA 判断线程栈并检查 EXECSTACK。结合本机地址记录和隔离前后对照，定位为探测页与线程栈合并造成的兼容问题。厂商完整内核及 AVC 日志未另行提取。参考 [Linux SELinux 实现](https://github.com/torvalds/linux/blob/v6.6/security/selinux/hooks.c) 和 [OpenJDK 21 探测实现](https://github.com/openjdk/jdk21u/blob/master/src/hotspot/os/linux/os_linux.cpp)。

`probe/assets/office/eva-java21-memory.c` 在原请求失败后检查调用方、页大小、权限组合、匿名私有映射及 dump 状态。符合条件时通过 MADV_DONTDUMP 隔离探测页，重试相同的 RWX 请求，再恢复 dump 状态。真实栈页被排除。后续请求失败仍会返回错误。

`eva-java21.py install` 按源文件和系统 JVM 摘要建立独立代际目录，编译兼容层，生成 JDK 工具启动入口，验证后原子切换 `current`。验证覆盖 javac、lambda、虚拟线程、循环计算及混合、解释、强制编译模式。普通应用进程也完成了这些验证。

手机入口为 `/root/.eva-runtime/java21/current`。`status` 检查当前 JVM 和兼容层摘要，`selftest` 执行实际验证。系统 JDK 更新后需要重新安装并验证。系统 Java 17 与原版 Java 21 文件保留。APK 构建器状态仍为 ready，并使用固定的 Java 17。

使用 [Ghidra 12.1.4 官方发行物](https://github.com/NationalSecurityAgency/ghidra/releases/tag/Ghidra_12.1.4_build)，文件为 `ghidra_12.1.4_PUBLIC_20260921.zip`。下载后核对官方发布元数据中的 SHA-256。

```text
ddac49f903da9d5bac833e5cc79395098b9c33cfd3279be5f31bd00387d2d4db
```

发行物包含原生反编译器源码、Apache-2.0 LICENSE 和第三方许可证。标准反编译器构建使用发行物内源码，无需检出源码仓库的子模块。手机执行以下构建，随后将 `ghidra_opt` 复制到安装目录的 `Ghidra/Features/Decompiler/os/linux_arm_64/decompile`。

```sh
make -j2 ghidra_opt ARCH_TYPE= OSDIR=linux_arm_64
```

安装目录为 `/root/.eva-runtime/ghidra/ghidra_12.1.4_PUBLIC`。本机原生反编译器 SHA-256 如下。

```text
6fd15e6033c542bd616796370c9595bb188a4b032e5a4f13e870ebcc337124a4
```

构建依赖来自签名 Alpine 仓库。许可证、版本、来源和包校验元数据保存在 `artifacts/java21-20261106/license-and-java17-check.txt`。OpenJDK 包保留 GPL-2.0-with-classpath-exception 元数据。

## REA 接入与验收

已读取并备份手机实际配置 `/root/.eva-codex/config.toml`，合并 REA 的 JAVA_HOME、GHIDRA_INSTALL_DIR、内存和启动超时设置，同时为 REA 子进程配置局部 LD_PRELOAD 与 EVA_JAVA21_COMPAT。REA 的 LaunchSupport 会解析真实 Java 路径，因此该进程环境也需携带兼容层。其他配置通过解析后对比确认保留。

`Java21RuntimeCheck` 通过实际 Android 宿主启动测试，记录的域为 `untrusted_app_34`。已完成以下检查。

- 编译并执行本机 ARM64 ELF 样例。
- Ghidra Headless 导入、自动分析和导出 `eva_transform` 的 C 伪代码。
- REA CLI 使用 Ghidra provider 返回同一函数的完整 Evidence。
- Eva 内核实际读回更新配置，并通过 `mcpServerStatus/list` 发现 REA 的 229 个工具。
- 24 次并发启动全部通过，真实 EACCES 权限失败在兼容层启用前后均保留。
- 升级前后 UI 会话数据库字节一致。

```c
int eva_transform(int a,int b)
{
  return a * 7 + b ^ 0x1357;
}
```

样例证明本机 Java 21、Ghidra 原生反编译器及 REA 调用链可用。大型文件的资源占用、其他处理器、GUI 调试器和其他原生插件需按任务单独验收。

## PRoot 路径兼容与记录

排查中发现 ADB 安装产生的部分模拟硬链接使用 `/data/user/0` 宿主前缀，与普通应用入口的 `/data/data` 规范路径存在可见性差异。核对两者设备号与 inode 一致后，规范化了 526 个软件包链接，逐项记录于 `hardlink-alias-repair.json`。`tools/runtime-device.py` 现在在验证两个目录指向同一对象后使用规范路径，新装 bash 在应用进程中可用。

本轮证据集中在 `artifacts/java21-20261106/`，包括完整 REA Evidence、样例源码及二进制、安装日志、Java 验证、配置读回摘要和升级前会话备份。配置原文备份仅保存在手机私有 repairs 目录。

清理检查和实际删除结果见该目录的 `cleanup.json`。运行依赖、最终兼容层、Ghidra 安装及其源码和许可证、可复用发行包与最终验收样例继续保留。
